# jumin-guide 설계

작성일: 2026-09-19

## 1. 문제

고령 1인가구가 받을 수 있는 복지서비스가 있는데도 **있는 줄 모르거나 신청을 못 한다.**

배경 수치:
- 2024-12 한국은 65세 이상 20% 초과 — UN 기준 초고령사회 진입
- 2026-08 기준 65세 이상 22.1%
- 1인가구 중 80세 이상 비중: 2022년 5.5% → 2052년 23.8% (통계청 장래가구추계)
- 전체 노인가구 중 독거 비율 약 36%

## 2. 이미 있는 것과 무엇이 다른가

**[보조금24](https://www.gov.kr/portal/rcvfvrSvc/main)** (정부24)가 같은 문제를 다룸.
중앙 1,000여 개 + 지자체 7,000여 개 + 공공기관 2,200여 개.

보조금24는 본인인증 후 **행정정보를 실제로 조회해서 확정**해준다. 행정정보 연계
권한이 필요하므로 개인은 따라갈 수 없다. **정확도로는 이길 수 없다.**

차별점은 보조금24의 구조적 빈틈 세 가지에서 나온다:

| 보조금24의 빈틈 | jumin-guide의 대응 |
|---|---|
| 본인인증 필수 — 고령자 이탈 1순위 | 로그인·인증 없음 |
| 결과 수백 개 나열 | 상위 3~5개로 좁히고 나머지는 접음 |
| "나"만 조회 가능 | 프로필 기반 — 누구 것이든 만들 수 있음 |

**세 번째가 핵심이다.** 자녀가 부모 대신 알아볼 방법이 사실상 없다.

## 3. 사용자

프로필을 만드는 사람과 프로필의 주인을 분리하지 않는다.

핵심 단위는 **"사람 한 명의 상황"(프로필)** 이고, 누가 만들었는지는 저장만 하고
로직에 쓰지 않는다. 이것만으로 아래가 전부 커버된다:

- 자녀 → 부모 (대표 시나리오, UX는 여기 맞춤)
- 본인
- 부모님 두 분 (프로필 2개)
- 형제·이웃·지인
- 사회복지사 (프로필 N개, 같은 코드)

**데이터·스키마는 좁히지 않고, 첫 화면·질문 순서·기본값만 고령 부모 케이스에 맞춘다.**
넓히는 건 구조로 하고, 좁히는 건 UX로 한다.

## 4. 기술 스택

Next.js 단일 레포 + Vercel 배포.

## 5. 핵심 결정 3개

### 결정 1: 로그인 없음, DB 없음

프로필(나이·소득·건강)은 서버에 저장하지 않는다. 클라이언트 상태로 들고,
결과 페이지 URL에 인코딩한다.

```
/result?p=eyJhZ2UiOjc4LCJyZWdpb24iOiLshJzsmrgi...
```

근거:
- 소득·건강 정보를 DB에 넣으면 개인정보처리방침·암호화·파기정책이 딸려온다
- 로그인은 고령 사용자 이탈 1순위 — 보조금24가 막히는 지점을 따라할 이유가 없다
- 자녀→부모 공유가 링크 하나로 끝난다. 계정 기반보다 낫다
- 회원가입·인증·비밀번호 재설정·세션을 만들지 않는다

**되돌리기 비용:** 프로필 여러 개 영구 관리나 제도 변경 알림이 필요해지면 계정이
필요해진다. 현재는 YAGNI로 제외.

### 결정 2: 복지 데이터는 빌드타임 스냅샷

API를 런타임에 호출하지 않는다. 빌드 시 전부 받아 JSON으로 커밋한다.

```
scripts/fetch-welfare.ts  →  data/welfare.json  (git 커밋)
```

근거:
- 복지 제도는 분기~연 단위로 바뀐다. 실시간일 이유가 없다
- data.go.kr API는 느리고 가끔 죽는다 — 런타임 의존 시 함께 죽는다
- API 키가 서버에도 올라가지 않는다
- 런타임 캐시·타임아웃·재시도·폴백을 만들지 않는다

갱신: Vercel cron 주 1회 재빌드.

### 결정 3: 규칙은 코드 안의 함수 배열

룰 DSL·규칙 DB·관리자 화면 없음. 30개면 TS 파일 몇 개다.

```ts
{
  id: 'basic-pension',
  serviceId: 'WLF0000...',        // 스냅샷의 서비스와 연결
  judge: (p) =>
    p.age < 65               ? no('만 65세 이상부터 해당됩니다')
  : p.incomeLevel === 'HIGH' ? unlikely('소득 하위 70%가 기준이라 어려울 수 있습니다')
  :                            likely('만 65세 이상, 소득 기준 충족 추정'),
}
```

**판정은 3값: `해당` / `아마 해당` / `해당 안 함` — 전부 이유를 동반한다.**

확정하지 않는 것이 중요하다. 행정정보를 볼 수 없으므로 확정이 원리적으로 불가능하고,
확정인 척하면 틀렸을 때 사람에게 실제 손해가 간다.

## 6. 데이터 소스

- [한국사회보장정보원_중앙부처복지서비스](https://www.data.go.kr/data/15090532/openapi.do) — 목록조회 + 상세조회
- [한국사회보장정보원_지자체복지서비스](https://www.data.go.kr/data/15108347/openapi.do) — 동일 구조

필터 파라미터(전부 범주형):
- `lifeArray` 생애주기
- `trgterIndvdlArray` 대상특성
- `intrsThemaArray` 관심주제
- `incomeLevel` 소득구간

**나이를 숫자로, 소득을 정확히 넣는 필터는 없다.** 범주 필터만으로는 수십~수백 개가
남는다. 그래서 규칙 판정이 필요하다.

## 7. 프로필 — 질문 6개

규칙이 실제로 읽는 필드만 둔다. 쓰지 않는 질문은 0개.

| # | 질문 | 값 | 가르는 것 |
|---|---|---|---|
| 1 | 나이 | 숫자 | 기초연금(65+), 장기요양(65+), 노인일자리(60/65+) |
| 2 | 사는 곳 | 시도 + 시군구 | 지자체 서비스 전체 |
| 3 | 소득 | 수급자 / 차상위 / 잘 모름 / 그 외 | 거의 모든 서비스의 1차 관문 |
| 4 | 가구 형태 | 혼자 / 배우자와 / 자녀와 | 독거 전용 서비스 |
| 5 | 거동·돌봄 | 불편 없음 / 도움 필요 / 장기요양등급 있음 | 장기요양·돌봄 계열 |
| 6 | 장애 등록 | 있음 / 없음 | 장애인 계열 |

**모든 질문에 "잘 모름"을 1급 선택지로 둔다.** 자녀가 부모 소득을 정확히 아는 경우가
드물다. 모름이면 해당 규칙은 `해당 안 함`이 아니라 **`확인 필요`** 로 간다.

한 화면에 질문 하나, 6단계.

## 8. 화면

```
/                 소개 + [시작하기]
/ask              질문 6개, 한 번에 하나
/result?p=...     판정 결과 · URL에 프로필 인코딩
```

결과 화면:

```
┌ 알아보실 만한 것  3개
│  기초연금
│  › 만 65세 이상, 소득 하위 70% 기준에 해당될 것 같습니다
│  › 신청: 주민센터 또는 국민연금공단        [상세 ▾]
├ 확인이 필요한 것  2개
│  노인맞춤돌봄서비스
│  › 소득을 모른다고 하셔서 판단이 어렵습니다. 주민센터에 문의해보세요
├ 그 외 서울 성북구 복지서비스 47개  [펼치기 ▾]
└
```

상위 3~5개가 전부이고 나머지는 접힌다.

## 9. 처리 흐름

```
스냅샷 전체 수천 개
  → API 범주 필터로 수백 개
  → 규칙 30개 판정  →  해당될 가능성 높음 (3~5개, 근거 포함)
                     →  확인 필요 (2~3개)
  → 나머지           →  그 외 목록 (접음)
```

## 10. 검증

규칙이 조용히 틀리는 것이 유일한 진짜 위험이다. 여기만 제대로 한다.

```ts
test('기초연금: 64세는 해당 안 됨, 65세는 해당')      // 경계값
test('소득 모름이면 "확인 필요"로 빠진다')             // 모름 처리
test('모든 규칙의 serviceId가 스냅샷에 실제로 존재한다')  // 아래 참고
```

세 번째가 가장 중요하다. 제도 이름이나 ID가 바뀌면 규칙이 **에러 없이 조용히 죽어**
결과에서 사라진다. 주간 재빌드 때 이 테스트가 깨지면 즉시 알 수 있다.

E2E·커버리지 목표는 두지 않는다.

## 11. 명시적으로 하지 않는 것

- 회원가입·로그인·세션
- 서버 DB
- 런타임 API 호출 및 그에 딸린 캐시·재시도·폴백
- 룰 DSL, 규칙 관리자 화면
- 네이티브 앱 (필요해지면 PWA로 감싼다)
- 신청 대행 — 안내까지만 하고 신청은 주민센터/해당 기관으로 보낸다

## 12. 나중에 붙일 자리

- **돌봄 공백 연결** (원래 관심사 3번): "대상이지만 대기 중"인 경우 이웃·자원봉사
  연결. 양면시장이라 공급자 확보가 선행 조건 — 이 프로젝트가 자리잡은 뒤에 별도 설계.
- 전 연령 확장: 스냅샷이 이미 전 연령을 담고 있어 데이터 작업은 불필요. 화면만 추가.
